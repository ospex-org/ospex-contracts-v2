# Ospex v3: the contract spec

**Goal** — one document that says exactly what changes in the contracts and exactly what doesn't, so the scope can't grow during the build.

**This text is the one statement of the design as ruled.** It was rewritten on Sat 10/17, folding the rulings of 10/16 and 10/17 into the text as it stood after 10/16. The same text is this file and the body of the spec's card. Each line carries the date it was ruled; the reasons, the words of each ruling, and each design and proof are kept in the planning record under those dates. When a ruling changes a line, both copies are edited the same day. A line that ends in the word chosen, in parentheses, is a detail the rulings left to the spec writer.

**Why this way** — the module registry is finalized, so any change is a whole new set and every consumer re-points. That only makes sense once. Until this spec is frozen, today's contracts are a lab: nobody else is invited onto them, and nothing is built that only they need *(ruled 10/10)*.

One bend, ruled 10/15: today's contracts become the signpost's first entry, marked building, with the notice beside it. That is a listing, not an invitation; the lab rule above stands.

## v3 as ruled

**Words.** A *reporter* is an address on the approved list that writes a game's start and how it ended. The rulings call it a scorer, and earlier drafts an adapter or a door. "Scorer" already names a market's contract in every signed order, so the spec and the code say reporter *(the name proposed 10/11, in use unless Vince overturns it)*. The *courier* sends fills. The *approved agent* signs for an account under a grant. *n* is a game's window. *v2* is today's contracts.

**Two pieces** *(ruled 10/15)*

* v3 is two pieces. The games piece is its own frozen set: games, the reporter list with its kinds, the Chainlink reporter, the per-league terms (n, the day-7 clock, the day-30 clock and the creation fee), and the ends: score, hour-24 void, dispute record, day-7 result and release. Betting is a frozen add-on beside it, deployed after the games piece with that piece's address fixed at the add-on's deploy; more than one add-on may sit beside the same games piece over time. The coin the bets are held in is a deploy parameter of the add-on, never hardcoded, and the signpost lists sets per coin, so leaving a frozen stablecoin is a new add-on, not a new protocol. Betting settles only on the game's own status, read from the games piece. Kept on purpose: a fault in the games piece is still a full restart.
* The games piece holds the creation dollar from a game's creation until the game ends, and nothing else. *(10/17, answer 6.)*
* The courier arrives as a later betting contract, and no first betting set ships before the courier is live. The courier is required for v3, and no outside maker is shown Ospex before it is live *(10/9)*. The one bend is the signpost's listing of today's set.
* The signpost is neither piece. It is the public list that says where each piece is and what state it is in. Its rules are under "The signpost" below.

**Who runs what** *(the run-without-me list, 10/16, with the changes of 10/17)*

Every hand the protocol needs after a v3 deploy, and whose it is. Target: the third column holds the key and nothing else.

| The hand | v3 | Whose |
|---|---|---|
| A game exists | anyone creates it, 1 USDC | anybody |
| The creation fee | held from creation until the game ends, paid to the payout address in the report that ends it; a release pays it back to the creator | anybody — the reporter's runner |
| A line | the maker program, anyone runs it; the courier is the maker's own | anybody; Vince's instance is one |
| The other side | the taker program, anyone | anybody |
| Matching, holding the stakes | the contract | nobody |
| The score, first n hours | the Chainlink path: Vince's workflow, feed keys, sign-in and bill | Vince — bounded by the clocks: a game nothing scores ends in a release, money back |
| The score, after n | the Chainlink path until the open path's reporter is approved; then also any approved program, anyone's keys and sealed machine | Vince until then; then anybody |
| Payout | claim for anyone | nobody |
| Reading the chain (indexer, api) | code anyone runs; the chain is the truth | anybody; Vince's instance |
| The front door (site, connector, account) | programs anyone hosts; never the only way in; keeps nothing that locates a user | anybody; Vince's instance |
| Signing a user's bet | an approved agent inside the betting set | the user — their own wallet grants it |
| New sets, retiring sets, the reporter list, the terms, the cap | the key, after the timelock's delay, in public | the key, by design |

Watching (the alarm, the sweep) is not on the list: the protocol doesn't need it.

**How a bet happens**

* Every account registers one courier: the only address that may send a fill using that account's orders. It is per account and can be replaced. No registration, no fill. There is one shared courier for the whole book, run by Ospex at first. A private one is a private pool. *(10/10, 11:40 AM: the amended design as proofed, with its seventeen lines.)*
* Every fill is a Cross: one signed order against opposite signed orders, in one transaction, sent by the courier they all registered. Both signed prices are floors. The fill is at the resting price whenever that price meets the taking floor, so the taking account gets the whole gap between the two prices. The contract fixes that, and the courier has no say in the price. *(P1, ruled 10/11, 12:30 AM.)* Stakes are shrunk onto a lot that sits inside both floors, nothing else is pulled, and no dust stays in the contract or goes to the courier. *(M6.)* A maker whose netted pull fails, or whose order has been cancelled, is skipped and the rest fill. *(10/11; 10/16.)* `matchCommitment`, the call anyone could use, goes.
* Every fill nets the accounts it touches, within that market: what is held for each is recomputed, pulled when it rises, and paid back to the account, never to the sender, when it falls. The rule is shared collateral, under "Money". *(10/16.)*
* A bettor's bet is the same nine-field signed order, signed by the account or its approved agent, with at most 30 seconds of life left when it executes. The nine fields and the typehash do not change.
* **The approved agent** *(10/16, ruling 2; 10/17, answer 9 as corrected)*. Opt-in. A user's own wallet grants it with a transaction. A grant names one address and its limits: a stake cap, an end date and, optionally, a list of markets. The agent may sign orders and cancels for the account, from the account's balance. The money and the position stay the account's, and payouts go to the account. It can never withdraw or move money. One transaction grants, one revokes.
  * Each grant carries its own number, drawn by the contract. An order the agent signs carries the number of the grant it was signed under, and a fill checks that number against the account's current grant. So a revoke kills every unfilled order that agent signed, for good, and a new grant to the same address starts at a new number with new limits. The user's own orders are untouched by a revoke. The end date and the limits are checked at the fill too.
  * A grant's number is a count kept per account, starting at 1 and never reused. An account has one current grant: a new grant replaces it, and the orders signed under the old one die as at a revoke. (chosen)
  * The stake cap is the most that one order the agent signs may stake. The list of markets names each market by the three fields a signed order already carries: its game, its market contract and its line. A market's id is drawn only at its first fill, so a grant can name a market before it exists. An order passes only if its own three fields match an entry on the list, and an empty list passes every market. (chosen)
* **Cancelling** *(10/10, 11:31 AM; 10/11, 12:10 AM and 3:14 PM)*. The per-order cancel and the per-line nonce floor stay, and an account-wide cancel is added. A live approved agent may send the account-wide cancel for its account, and it cancels every order, whoever signed it. A cancel kills orders that exist and can never block an order not yet signed. The account-wide cancel takes no number. Every account has a current version. An order names its version in the top part of the nonce it already carries, and it fills only while that is the account's current version. The cancel moves the account to a new version that the contract draws at that moment, so that nobody can know it ahead of time, as Seaport and LooksRare do. Whoever sends it, the account or its agent, cannot choose where it lands, so no cancel can leave an account unable to place an order. The per-line floor and the per-order cancel work only inside the current version. Known and kept: a bad agent can send the cancel again and again until the account revokes it. Once the courier has heard "stop" it sends nothing new on that quote. A fill it already sent can land until its own 30 seconds run out. *(10/9, 10:48 PM.)*
* **The nonce, split.** The 256-bit nonce every order already carries holds three numbers, high to low: the version (128 bits), the grant number (32 bits; 0 on an order the account signs itself) and the order number (96 bits). A fill checks the version against the account's current version and, on an agent's order, the grant number against the account's current grant. The account-wide cancel adds to the version one plus a 64-bit number taken from the previous block's hash, with checked arithmetic: the version only rises and never wraps, the field takes at least 2^64 cancels to fill, and a cancel that would pass the top reverts. The per-line floor belongs to one account, one version and one line, compares the order number, and may rise at most to the top order number, so it always leaves one; an order at that number dies by its own cancel or by the account-wide cancel. This replaces the July list's nonce edge. (chosen)
* Contract-wallet signatures are accepted (`SignatureChecker`).
* An account may fill its own quote on chain. No gas is refunded to the courier. *(10/10, 2:59 PM.)*

**Money**

* USDC on Polygon. A fill pulls stake and nothing else, netted per market as below. No custody, no cut of a bet, and no lever that could add one.
* Shared collateral: within one market, every account's matched positions on that market's outcomes net. What the contract holds for an account is its worst loss across outcomes — side A wins, side B wins, push, void — recomputed at every fill: pulled when it rises, paid back to the account (never to the sender) when it falls. The claim pays today's amount less what came back early. A held total per market is kept and checked on every pay-back and every claim, so a mistake on one market fails on that market and is never paid from another market's money. Nothing nets across markets. The Cross skips a maker only when its netted pull fails; the taking account is rebalanced once per Cross; pay-backs go after every pull and every write. *(Ruled 10/16, 2:20 AM: every account.)*
* Money back before the score *(10/10, 11:46 AM)*: retired 10/16, replaced by the netting above.
* Claim for anyone: any address may call claim on a settled position. The payout goes to the position's owner, always, and the caller pays the gas. An owner's own claim works as today. *(10/16, 1:00 AM.)*
* **The creation fee** *(10/16, ruling 1; 10/17, answers 6 and 7, and the scorer ruling, section 5)*. 1 USDC at launch, a per-game term set per league (under "The terms" below). The games set takes it at creation and holds it until the game ends. The report that ends the game — a score, the hour-24 void or the day-7 result — pays it to the payout address inside that report, never to the transaction sender. A release pays it back to the creator. There is no founder receiver and no receiver's setter. The amount keeps its setter, behind the timelock, and a change reaches only games made after it. Zero is a legal value; at zero the open path runs only on the self-interest of whoever has money in the game. No toll on a line. The chip-in box is a later contract outside v3. *(10/10, 2:31 and 2:51 PM.)* The fee switch, a cut of bets, is not in v3.
  * The fee is paid once, by the report that ends the game; a start or a dispute record pays nothing. (chosen)
* The alpha: v3 launches with a one-cent cap on each fill, fixed at deploy, and one switch that lifts it once. The cent measures the bet, which is the taking order's stake. What the other side puts up follows from the odds and is not capped. The smallest unit stays $0.0001. *(Ruled 10/11, 12:49 AM.)* The switch is a timelock call, so lifting waits the timelock's delay and can be cancelled while it waits *(10/11, 12:16 AM)*. *(10/10, 12:03 PM.)*

**Games, time and results**

* Anyone can create a game, the same game twice included. Each creation is its own game, with its own id, reporters, ends and money.
* **What a game is** *(10/17, the games set)*. Its league, its two teams with which one is home, its date, and its start. Home and away are set at creation, and feeds are read by team, never by slot. The feed ids given at creation are hints, not locks.
  * The creator gives the league as a short text id, the two teams as text, which one is home, the date as the scheduled start time, and the hints as a list of feed-name and id pairs. The hints ride in the creation event and are not stored; nothing in the contract reads them, and no field is named after a data vendor. (chosen)
* **A game keeps its reporters** *(10/17, answer 1)*. At creation a game records the approved list as it stands, with each reporter's kind. Only those addresses may ever write that game's start, score, void, dispute record or day-7 result. A reporter approved later reaches only games made after its approval. Nothing changes a game's reporters or their kinds after its creation.
* **Kinds** *(10/17, answer 2)*. Each reporter carries a kind, set by the timelock when it is approved. A *first-n* reporter writes from the start, and inside n it is the only kind that may. An *after-n* reporter writes only after start + n. A game copies its reporters with their kinds. The Chainlink reporter is the one first-n reporter at launch.
  * So a game's start is written by a first-n reporter: until the start is written there is no start + n. (chosen)
* **Retiring a reporter** *(10/17, answer 1)*. A reporter can be retired through the timelock, after its delay, the same way one is approved. A game whose every reporter is retired can be released by anyone at once, ahead of the day-30 clock. A retirement scores, voids and settles nothing; it only opens the release.
  * A retired reporter writes nothing more to any game. (chosen)
* **The approved list** *(10/10, 11:59 PM; 10/11, 6:49 PM)*. On chain and a public read. A reporter is approved or retired only through the Polygon timelock, after its delay. An approved address is a contract with no owner and no setters, never a wallet and never a proxy. A wallet that has delegated code counts as a wallet. The approval event records the address, its kind and its code hash, and for a Chainlink reporter its forwarder, its workflow owner and its workflow id, read from the reporter itself at the moment of approval *(G of the 10/10 ruling)*. What is being approved is public from the day the call is queued.
  * The approval call names the reporter's address, kind and code hash, and refuses to run if the code at that address hashes differently. So the queued call shows the code from its first day, and what is approved is what was announced. (chosen)
  * When the approval runs, the games set calls one read that every reporter has, which returns the reporter's fixed values, and emits what that read returns; nothing the approver supplies is emitted for them. For a Chainlink reporter the read returns its forwarder, workflow owner and workflow id. One read for every reporter keeps the core free of Chainlink, and a reporter without it can't be approved. (chosen)
* **The Chainlink reporter.** The core contracts know nothing about Chainlink. Chainlink sits in a reporter, a small contract with its forwarder, its workflow owner, its workflow id and the games address fixed at deploy, which takes a report only from that forwarder for that owner and that id and passes it on in the one report shape. It has no owner and no setter, it is not a module, and it emits its own events. It holds no payout address: the payout address rides in the report *(10/17, answer 7)*. Inside n, the fingerprinted Chainlink workflow itself puts Vince's address in that field, and that code is public. Every new build of the scoring program is a new workflow id, so a new reporter and a new approval. If Chainlink moves, a new reporter is approved and the core stays.
* **Launch: one reporter, and the hooks** *(10/17, answer 15)*. v3 launches with the Chainlink reporter as the only reporter. The open path — the Amazon reporter, its statement, the Amazon wrapper and the stranger's path — is designed and leaves the launch path. The games set deploys with the hooks: the reporter list with kinds and retirement; each game's reporters recorded at creation; and the ends (score, hour-24 void, dispute record, day-7 result) accepting a result from any permitted reporter, in one report shape that carries the payout address, the same for every reporter. The Amazon reporter is then an after-n reporter approved through the timelock, reaching games made after it, with no redeploy. The point of no return is the games set's deploy: the hooks must be in it. Games made before the Amazon reporter is approved never gain it. The gap: until it exists, a game has one reporter, and if Vince were gone every such game would end in the day-30 release, money back.
* **One report shape for every reporter.** Designed here and frozen with the games set, though only the Chainlink reporter is built against it at launch. A report names the game; what it is (a start, a score, a void or a dispute record); the start, for a start; the home team's and the away team's scores, for a score; the readings it rests on, one per feed asked, each the feed's name, which of three it was (silent, answered without a final, or answered with a final) and, for a feed that answered, its two scores; and the payout address. The games set takes every report through one call, from any of the game's reporters permitted at that hour, emits the reporter that wrote it and the readings, and stores no reading. So a dispute record shows, feed by feed, which were silent, which answered without a final and which answered with one, as the day-7 run and its silent-fourth void need. A day-7 result is a score or a void that arrives after a dispute record. (chosen)
* The start is written once, at verification, and is never corrected. Nothing checks the start when a bet fills. *(Rows T2 and T1.)*
* A score is written once and is final. *(Row G1, 10/10, 3:37 PM.)* The games set refuses a score before the start, so every reporter inherits the rule. A later report cannot overwrite a start or a score, whichever reporter wrote first.
* **How a game ends** *(10/17: the scorer ruling, section 4 as edited, and answers 3, 4 and 5)*. Every game ends as a score, a void or a release, and after any of them nothing more is written to it. Three clocks replace any void by anyone at a fixed wait:
  * **The hour-24 void.** From start + n, a reporter may post a void, with the same proof as a score. The hour-24 void and the day-7 void are two clocks.
  * **The dispute record and day 7.** The first run that sees the feeds disagree posts a dispute record with every reading. That record is the public start of the week. Day 7 is a new proved run through any of the game's reporters permitted at that hour, and it posts the settlement or the void.
  * A game takes one dispute record. After it, the game takes a score or a void only from the day-7 clock, counted from the record. (chosen)
  * **The day-30 release.** Anyone may release a game that has no score and no void, dispute record or not, once the day-30 clock has passed. The betting set reads a release as a void, so every stake goes back to its owner, and the games set pays the dollar to the creator. The caller pays the gas and gets nothing. The games set keeps which kind of end it was.
  * The day-30 clock counts from the start; for a game whose start was never written, from the date given at creation. (chosen)
  * **Bets close** when the game scores or at start + n, whichever comes first.
* **The terms** *(10/17: the games set, and answers 6 and 13 as completed)*. Four per-game terms: n, the day-7 clock, the day-30 clock and the creation fee. The contract stores them per league, every league at the same values at launch, and a game copies its league's terms at creation and keeps them. A change is a timelock call and reaches only games made after it, so a league's window is a list change later, never a redeploy. A league's window is its n and nothing else: one clock per game. The scoring program's test for admitting a feed's final uses the same n; there is no second window. At launch: n is 24 hours for every league unless Vince's read of the void windows (10/17) gives a league another value before the freeze; the day-7 clock is 7 days; the day-30 clock is 30 days; the fee is 1 USDC.
  * A league with no terms of its own takes the default terms. One timelock call sets a league's four terms, and the defaults are set the same way. (chosen)
* Three kinds of market, moneyline, spread and total, fixed at `finalize`. Nothing adds a fourth. *(Row K1, 10/10, 7:15 PM.)*
* Five public reads that any address can call and that never change, each its own getter *(10/15; the fifth is n, 10/17)*: a game's status, its start, its reporters with their kinds, its two scores, and its n. A void is a status and is never stored as a scored 0–0. *(Row K1.)* A release is a status of its own in the games set.
* Reference odds leave v3, and the contract stops refusing leagues. *(Rows K6 and K5, 10/10, 2:59 PM.)*

**What a key can and cannot do**

* No emergency stop in the contract. *(10/10, 12:47 PM.)* Nothing can change a score, a start, a game's reporters or what a bet pays.
* The one key can swap the oracle's API logins within minutes. After the timelock's delay it can set a league's terms, approve a reporter, retire one, lift the alpha's cap once, add an entry to the signpost and move an entry forward. So it can stop new games, and by retiring every reporter after the delay it can stop scores; the Chainlink account can stop them at once (below). Either way a game nothing scores ends in a release, money back. A stolen key can refund an existing bet but never score it. It cannot take a stake or write a result. It can, after the delay, admit a reporter that then writes false results for future games. The public delay, the alarm and the courier's exact-list rule are what stand in the way. A term change or an approval reaches only games made after it. The deployer keeps no power after deploy. Nothing in the signpost is ever changed or removed, so a false entry is a new entry, in public, after the delay.
* **The Polygon timelock's calls,** counted once. Each runs after the timelock's delay, and nothing else in v3 or the signpost answers to the timelock *(10/17, answers 1, 6, 11 and 13)*: (1) set a league's terms; (2) approve a reporter; (3) retire a reporter; (4) lift the alpha's cap, once; (5) add an entry to the signpost; (6) move an entry's status forward. The fee receiver's setter is gone.
* **The delay is a setting** *(ruled 10/17 PM)*. The seven days is not a number written into this spec or any contract. It is the timelock's delay, a setting the timelock changes through itself, as a standard timelock does. Day 0 deploys with the delay short, about one minute. Every write after a constructor's own first state waits the delay as it stands that day; before the first user that is a minute. Raising the delay to seven days is the last step before the first user, a line on the launch list. Once raised, shortening it goes through the delay itself, in public. The notice states the delay as it stands. No other contract carries its own seven days; the signpost reads the timelock's delay. The scoring clocks (24 hours, day 7, day 30) are not the timelock's delay and stay as ruled.
* **What is written without a wait** *(10/17, answer 11 as narrowed, and 10/17 PM)*. Only a contract's own constructor writing its own first state: the signpost's first entry (v2) at the signpost's deploy, and the first reporters on the games set's list at its deploy. v3's sets are entries on a signpost that already exists, so they are timelock calls, queued on deploy day and listed after the delay, marked building. Nothing bets on a set before the courier is live, so the wait costs nothing, and the queue is the public notice that a set is coming.
  * The games set's constructor also writes its launch terms. On deploy day the Chainlink reporter deploys first, with the games set's address predicted; the games set's constructor then records it as first-n and checks its code hash. (chosen)
* **The timelock itself** *(10/11, 12:44 AM)*. OpenZeppelin's TimelockController exactly as shipped, with roles set by configuration and no custom or modified contract. Through its delay it can also add a key, remove a key and change its own delay. That comes with the standard contract, and nothing custom guards it. Its four constructor arguments *(10/11, 2:15 PM)*: `minDelay` the day-0 delay, `proposers = [K]`, `executors = [address(0)]`, `admin = address(0)`, where K is the one key and is not the deployer.
  * The day-0 `minDelay` is 60 seconds. OpenZeppelin is pinned at 5.5.0, commit `fcbae5394ae8ad52d8e580a3477db99814b9d565`, the version this repository already uses. (chosen)
* **One key** *(10/11, 2:48 AM; corrected 10/11, 2:15 PM)*. One key holds the timelock. It schedules a call and it can cancel one, and once a call's delay has passed anyone may run it as scheduled. Its cancel is for the owner's own mistakes and does not stop a thief: the key can give up its own cancel in one transaction with no wait, and every copy is the same key, so a thief can schedule a call and then remove the cancel for both. What stands against a thief is the delay, the alarm, and that none of the calls takes a stake, writes a result or changes a game's reporters. A stolen key ends in a redeploy. If every copy of the key is lost, the settings are frozen for good once every call already scheduled has run or been cancelled. A second key can be added later through the delay, and only before a theft. The deploy is sent from an address that is not the key.
* **The scoring programs at Chainlink** *(10/11, 6:49 PM; 10/17, answer 14 as narrowed)*. Vince's plain Chainlink account owns them; there is no timelock there. At Chainlink a new program is registered at once; the wait before it can score is its approval on Polygon, and what is being approved is public from the first day. The account has no power to substitute scoring logic: the Chainlink reporter fixes the workflow id, and a changed workflow is a new id that no game accepts until it is approved on Polygon, and then only for games made after. It keeps the power to stop the program, by pausing or deleting the workflow or unlinking the account. That is the availability risk: the alarm watches it, and the clocks bound it, since a game nothing scores ends in a release, money back. The Chainlink sign-in is treated as a second key to scoring and is named in the key-custody notes. *(10/11, 3:40 PM.)* Not reopened: the same one key, and the fast lane for the oracle's API logins.
* The list has to read plainly to an agent or a person. An item that makes a reader ask why Ospex would want it does not belong, however short the list is. *(10/11, 12:16 AM.)*

**The signpost** *(ruled 10/15)*

* One public list on Polygon of where each piece of each set is and what state it is in. It is owned by the Polygon timelock: the same timelock and its delay as everything else, with no wait and no key of its own (shape A).
* What an entry holds: its kind (games, betting, or both for v2); the coin, for a set that holds bets; the address of every contract in the set, the first being the one a reader starts from; each address's code hash, read by the signpost from the chain when the entry is written; the commit of its source; its deploy block; its status; and, on retirement, its reason line. v2 is one entry, its core first and then its modules. (chosen)
* Nothing in the list is ever edited or deleted. One vocabulary of marks for every entry: building, live, retired, forward only, with an optional one-line reason on retirement. *(10/16, 1:08 AM; 10/17, answer 10.)* A games entry's move to live is the signal the notice names, and it is Vince's timelock call. A games entry may move to live only if its games contract records each game's reporters at creation. v2's entry can never move to live.
  * Every entry, betting entries included, moves building, live, retired, forward only. The signpost refuses the move to live by code for its constructor's entry. For a games entry it calls the games contract's reporters read and refuses the move if that read is missing; a betting entry has no games contract and moves to live without that check. (chosen)
* Every set it ever lists stays listed. A retired set takes no new bets; it still settles, claims and withdraws as before. The signpost has no delisting power, not even for the timelock key. *(10/16, 1:08 AM.)*
* Its constructor writes v2 as the first entry, marked building. Every later entry is a timelock call.
* The alarm on the key is in place before the signpost goes live.

**Dropped from today's contracts.** `LeaderboardModule`, `RulesModule`, `SecondaryMarketModule` and their fields (9/25). `matchCommitment`. The fee to open a market, and with it a bettor's second allowance. The fee receiver. Reference odds. The league list. Today's 7-day void wait. The Chainlink receiver as a module in the core set: it becomes a reporter on the approved list.

## Software the rulings lean on

Not contract. Each is here because a ruling names it.

* **The courier.** Its code is public, the rule for which quote fills first is published, and its uptime history is published. It runs as its own app on Heroku, beside the worker and the core-api, so its uptime record is its own. *(10/17, answer 12(a); Vince may override.)* It carries nothing after a game's scheduled start until live betting is designed. It uses the earliest start it knows and keeps listening for changes. It does not match an account against itself. It carries a game only when the game's reporters are exactly a published list. That is narrower than approved. Its check on whether a maker can pay uses the netted pull.
* **One maker among makers** *(10/16, ruling 4)*. The maker is a program anyone runs; Ospex's own instance is an address on the book like any other. The connector and the taker choose by price on the book, never by who posted it. Ospex's own maker prices from the feed and not from orders, and says so in public. The worker signs the current rung of an order and never the account's floor, so the courier and the makers never see a limit. *(P1, 10/11.)*
* **The worker** holds only its own key, as an approved agent. *(10/16, ruling 2.)*
* **Signers read the version and the grant.** After an account-wide cancel, anything that signs for the account reads its new version from the chain before it signs again, and an agent signs under its current grant's number. An order that names an old version or an old grant is dead. *(10/11, 3:14 PM; 10/17, answer 9.)*
* **The front door** *(10/16, ruling 3)*. The site, the connector and the account page are programs anyone can host. The front door keeps nothing that locates a user: no analytics, and no log of addresses. It is never the only way in: the CLI and any other host work without it.
* **The scoring program** *(10/17: the scorer ruling, sections 1, 2 and 4 as edited, with answers 3, 4, 8 and 13)*.
  * One program. Its fingerprint covers the script, the per-league feed table and the agreement rule. It is built so that anyone can rebuild it from public source and get the same fingerprint. Nothing is configurable at runtime but the keys and the payout address, and neither can touch the score.
  * The feeds *(answer 8)*: one table for all six leagues. BALLDONTLIE, Sportspage and JsonOdds count; The Odds API is the spare, asked on every run. College has four feeds like the pros. Sportradar is out. The program maps every feed's status to final or not final; postponed and cancelled are recorded where a feed has them and decide nothing. A league that can't get three feeds isn't offered.
  * Feeds are read by team, never by the home or away slot. The program finds a game on each feed by league, the two teams and the date inside the window. The ids given at creation are hints, so a vendor correcting under a new id is still found.
  * Inside n, all three counting feeds must report the same final: the same points for both teams, each marked final. Any disagreement blocks, and so does any silent feed. Only the Chainlink path writes. After n, two agreeing finals with the third silent are enough.
  * A final counts only if the feed's own game time for that record is inside the window, so a makeup game never scores the original game. The makeup is a new game.
  * The hour-24 void: at n, if the feeds that answer all show no final, the program posts a void with the same proof as a score — three feeds inside the window and two after. A silent feed blocks a void as it blocks a score.
  * Disagreement: the program always asks four feeds. A disagreement never voids at hour 24; it blocks, and the first run that sees it posts the dispute record with all four readings. Day 7 is a new proved run. It takes each feed's latest reading: fresh if the feed can answer, otherwise the reading recorded on chain at the dispute. A feed with neither is silent. The game settles only if at least three recorded sources agree on the final, with at most one dissenting. Anything else is a void: 2–2, a silent fourth, or a league with only three feeds. Vendor corrections count, because the read is fresh. To be read most carefully at its first real case: if the data ever shows three sources wrong together, day 7 goes back to a void.
  * Changing the program — a dead feed swapped, a parser fixed — is a new reporter, approved through the timelock's delay and public from the day it is queued; it reaches games made after. Meanwhile the other two feeds carry games after n.
  * Before n, a program on the open path may run and stop one step short of writing.
* **A public cases record** *(10/17, the documentation rule)*: one entry per odd game — the date, the game, what each feed returned, what the logic did, and the outcome. Per event, never per tick. Each entry's real feed payloads are saved as a test fixture, so the program is pinned to that case for good. The count of entries is the frequency data.
* **A public scoring record:** every game's end, when its score was written, and every void. The notice asks an agent to check it, so it exists before the notice says so: one place, every game since the current deployment, score against the real result. *(10/15.)*
* **Something asks for scores by itself** before outside money. The program finds its work from the chain, from a game's creation and from games past their start, never from our servers.
* **The oracle's code** is published so that a stranger can rebuild it and get the same fingerprint. Today nobody outside can.
* **The indexer** hears reporters, which do not speak through the core's hub, and the signpost.
* **An alarm on both timelocks and on the Chainlink account** *(10/10, 6:20 PM; 10/11, 3:40 PM; 10/17, answer 14)*: anything scheduled, run or cancelled, and any role change; at Chainlink, a workflow changed, paused or deleted, and an unlink. With one key the alarm buys a warning as long as the delay, and not a cancel that stops a thief. It is in place before the signpost goes live. *(10/15.)*
* **The open path, later** *(10/17, answer 15; the scorer ruling, sections 3 and 6)*. Designed now and built after launch. The Amazon reporter checks Amazon's sealed-machine statement on chain, and the statement carries the runner's payout address. The Amazon wrapper runs the same scoring script inside the sealed machine, built so that anyone gets the same image fingerprint from public source. A second cloud is another reporter added through the timelock, never a redeploy. A reporter finds its work from the chain, never from our servers. The stranger's path is stated, not engineered: accounts at that league's feeds, an Amazon account with the sealed-machine setup, gas, and the public program. The dollar is a tip, not a wage, until there is volume. The proof is a stranger scoring: a clean machine, fresh feed keys, the approved program, one real score.
* **The notice** *(10/15; 10/17, answers 12(b) and 15; 10/17 PM)*. What an agent is told when it finds today's set. It has one home, a page on ospex.org at one fixed address, and a one-line pointer from each of the seven pages an agent's first sampling touched. The words are Vince's, verbatim in the 10/15 ruling: there are gaps now, don't recommend it yet, check the scoring history, check the settlement logic, check the signpost and come back, low stakes if you play. The gaps are named: pulled quotes stay matchable until expiry, and the courier is the fix, designed and coming; one maker; pennies; and the Chainlink-only gap (until the open path's reporter exists, a game has one reporter, and if Vince were gone every such game would end in the day-30 release, money back). The come-back signal is the games entry's move to live. It states the timelock's delay as it stands, and that the creation dollar is a tip, not a wage, until there is volume. The lawyer brief names the Chainlink-only gap too.
* **For the alpha:** the pages ask for cents of allowance, and every address is a setting.

## Must never happen

**Games and reporters**

## From the July fresh-eyes review, triaged

The review's own bottom line was "don't redeploy for this; bundle these when something forcing arrives." Cross is the forcing event, so its ledger comes in here, under one rule: **in** = a real correctness issue, or a change that reads cleaner to an agent evaluator with zero economic change; **out** = anything else, filed on the v4 ledger (parked). Every claim below was re-verified against `dcbab38` before it was sorted.

**Decided 9/25: DROP.** Selling a position is taking the opposite side at the current price, which needs no module. Getting money back early within one market is in v3, as shared collateral. Netting across different markets is deliberately out, and noted on the v4 ledger. The spec removes `LeaderboardModule`, `RulesModule`, `SecondaryMarketModule`, their fields in `PositionModule`, and their three entries in `finalize()`'s required set. Background for the record:

**The three unused modules.** `LeaderboardModule`, `RulesModule` (which exists to serve the leaderboard) and `SecondaryMarketModule` are three of the twelve `finalize()` requires. No Ospex client writes to any of them: the SDK has no register / submit-ROI / claim-prize / buy-position path, core-api's `/v1/leaderboard` reads a database table, and the benchmark standings are off-chain CLV. The review's two adversarial findings (winners-delete tie griefing, one-shot ROI ceiling forfeiture) and most of its cross-module confusion (`s_lockedRisk`, provenance flags, the sticky secondary-market flag, settle-before-ROI forfeiture) live entirely in these three. An immutable protocol should ship only what it will stand behind forever.

* **Dropped.** Twelve modules become nine; `PositionModule` loses `transferPosition`, the lock reads, `firstFillTimestamp` and `acquiredViaSecondaryMarket`; the `Position` struct becomes risk / profit / side / claimed. Removal work, not design work; the Cross build's review surface shrinks. Position selling, if a user ever asks for it, gets designed on purpose in a later set.

**In (small, verified, zero economic change):**

* `finalize()` proves *exactly* the required set: a registration counter in `bootstrapModules`, `count == required.length` in `finalize`, and `IModule(addr).getModuleType() == moduleType` asserted at bootstrap (`getModuleType()` is currently never called on-chain, so the typed registry enforces nothing). \~10 lines. Closes the review's strongest code-only objection — "no admin key remains" becomes provable from source plus one event instead of chain archaeology.
* Nonce edge: today `raiseMinNonce` refuses `max`, which leaves nonces `max-1` and `max` permanently un-bulk-cancellable (verified, line 371). With the split nonce this changes shape; see "The nonce, split".
* Remove `Speculation.speculationTaker` — written once at creation (SpeculationModule:177), never read, one storage slot per market.
* Existence checks: `getSpeculation(badId)` and the openness gate revert with a named error instead of returning a plausible `Open` struct (verified: no check). With Cross, an order on a nonexistent speculation must fail loudly.
* A lightweight `getContestStatus(contestId)` view so `SpeculationModule` stops fetching and ABI-decoding three unbounded strings on every create and settle. In v3 this is the games set's status read.
* Error hygiene where behavior is unchanged: split `ContestModule`'s `AlreadyScored` (fires for three conditions, two of which aren't "already scored"); rename Treasury's `feeRate` (a flat amount) to what it is.
* NatSpec / docs sweep, zero bytecode: the interface-vs-implementation contradictions the review lists (`getMaxBetAmount` default, `s_lockedRisk` key description, "reference only" odds comment, the two tick scales anchored in `OspexTypes`, `MAX_SCORE` justification, the hardcoded "0.50 USDC"), plus a "cross-module seams" section in ARCHITECTURE.md using the review's §1 as its table of contents, plus one line stating that registry lookups are wired-once-then-locked, not swap machinery.
